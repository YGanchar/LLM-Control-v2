# Анализ архитектуры LLM-Control-v2

## 1. Обзор проекта

**LLM-Control v2** — десктопное приложение на PySide6 для управления локальным сервером с GPU и запуска llama-server. Приложение предназначено для работы с удалённым RTX-сервером через SSH, Wake-on-LAN и мониторинг ресурсов в реальном времени.

**Основные функции:**
- Сканирование `.gguf` моделей на локальном диске
- Генерация и редактирование `.mod` файлов конфигурации для llama-server
- Управление инстансами сервера через SSH: старт/стоп/перезапуск, применение конфига, просмотр логов
- Мониторинг ресурсов сервера: CPU, RAM, GPU, статус инстансов
- Управление питанием сервера через Wake-on-LAN и SSH shutdown

## 2. Структура файлов и компонентов

### Корневые файлы
- `main.py` — точка входа, загрузка `.env`, инициализация QApplication, запуск MainWindow
- `main_ui.py` — главное окно с тремя вкладками, координация виджетов, статус-бар
- `scanner_widget.py` — UI сканера моделей, таблица с результатами
- `config_widget.py` — UI конфигуратора `.mod` файлов, генерация авто-конфига
- `server_widget.py` — UI управления сервером, кнопки управления инстансами
- `model_layers.json` — маппинг размеров моделей → количество слоёв n_layer
- `ИНСТРУКЦИЯ.md`, `структура.txt` — документация

### Services
- `services/model_scanner.py` — рекурсивный обход файловой системы, поиск файлов по расширению
- `services/mod_generator.py` — генерация `.mod` файлов, преобразование клиентских путей в серверные
- `services/system_monitor.py` — RemoteMonitorThread, сбор метрик по SSH, WoL, shutdown
- `services/server_control.py` — локальный контроль процессов llama-server через psutil
- `services/ssh_setup.py` — генерация и копирование SSH-ключей, тест соединения

## 3. Потоки данных и взаимодействия

### Поток 1: Сканирование → Конфигурация
1. Пользователь выбирает путь сканирования в ScannerWidget
2. `find_files_by_extension` ищет `*.gguf` рекурсивно
3. Определяется наличие vision-моделей по наличию файлов `mmproj`, `clip-`, `vision`
4. Двойной клик по модели → сигнал `model_selected` → MainWindow → ConfigWidget.set_model
5. ConfigWidget генерирует авто-конфиг на основе размера модели, квантизации, GPU_RAM_GB

### Поток 2: Генерация конфига
1. `EnvConfig` загружает параметры из `.env`
2. `to_server_model_path` преобразует клиентский путь `/media/rtx-models/...` → серверный `/srv/models/...`
3. `ModParams` валидирует параметры перед сохранением
4. `build_mod_content` формирует текст `.mod` файла с MODEL, HOST, PORT, THREADS, CTX, BATCH, NGL, EXTRA
5. Сохранение в `LAST_MODS_PATH`

### Поток 3: Управление сервером
1. ServerWidget получает конфиг из ConfigWidget через сигнал `run_command_requested`
2. Валидация конфига: проверка обязательных полей, диапазона порта, минимального CTX
3. Конфиг отправляется на сервер через SSH: запись в `/media/rtx-storage/llama-mode.conf`
4. Команды `llmctl` выполняются через SSH: start/stop/restart/status
5. Логи и статус читаются через SSH

### Поток 4: Мониторинг
1. `RemoteMonitorThread` работает в фоне каждые 2 секунды
2. Подключение по SSH с использованием ключа `id_ed25519_llm`
3. Сбор метрик: CPU/RAM через `top`/`free`, PID llama-server через `pgrep`, GPU через `nvidia-smi`
4. Сигнал `metrics_received` → MainWindow → обновление статус-бара

## 4. Конфигурация и окружение

Файл `.env` содержит:
- `LAST_SCAN_PATH` — путь для сканирования моделей
- `LAST_MODS_PATH` — путь сохранения `.mod` файлов
- `SSH_HOST`, `SERVER_HOST`, `SERVER_USER`, `SERVER_MAC` — параметры SSH и WoL
- `DEFAULT_CONFIG_PATH`, `SECOND_CONFIG_PATH` — пути к конфигам на сервере
- `GPU_RAM_GB` — объём VRAM для авто-подбора параметров

## 5. Сильные стороны

- Единый интерфейс для сканирования, конфигурации и управления
- Авто-подбор параметров на основе размера модели и VRAM
- Мониторинг ресурсов в реальном времени
- Wake-on-LAN и удалённое выключение сервера
- Использование SSH-ключей вместо паролей
- Преобразование путей клиент → сервер

## 6. Слабые стороны и технический долг

### Архитектурные
- Смешение ответственностей: UI содержит бизнес-логику генерации конфига
- Отсутствие слоя сервисов: логика размазана между виджетами и services
- Жёсткая связанность с Qt: невозможно тестировать без GUI
- Отсутствие DI/IOC: зависимости создаются внутри конструкторов
- Хардкод путей: `/media/rtx-models`, `/srv/models` зашиты в коде

### Код
- Отсутствие валидации входных данных в UI
- Использование `os.getenv` напрямую в виджетах
- Генерация конфига в UI, а не в отдельном сервисе
- Отсутствие обработки ошибок сети и SSH
- `RemoteMonitorThread` выполняет SSH-команды синхронно, блокируя поток
- Отсутствие логирования действий пользователя

### Безопасность
- SSH-ключи хранятся в `~/.ssh`, без шифрования
- Пароли не используются, но ключи могут быть без passphrase
- `sudoers` настройка для `llmctl` требует ручной настройки
- Отсутствие проверки целостности конфигов перед отправкой
- Возможность выполнения произвольных команд через `llmctl`

### Тестируемость
- Нет unit тестов
- Отсутствие моков для SSH и файловой системы
- Сложно тестировать из-за сильной связанности с Qt
- `model_scanner` использует `os.scandir` напрямую

## 7. Риски

- **Потеря данных**: ошибка при записи `.mod` файла может повредить конфигурацию
- **Недоступность сервера**: падение SSH-соединения приводит к зависанию UI
- **Неправильный авто-подбор**: неверные параметры могут привести к OOM на GPU
- **Безопасность**: SSH-ключи могут быть скомпрометированы
- **Масштабируемость**: приложение не готово к работе с несколькими серверами
- **Поддерживаемость**: код сложно поддерживать из-за смешения UI и логики

## 8. Рекомендации по рефакторингу

### Архитектура
1. Внедрить слои: UI → Application Service → Domain Service → Infrastructure
2. Вынести бизнес-логику из виджетов в отдельные сервисы
3. Внедрить абстракции для SSH, файловой системы, мониторинга
4. Использовать Pydantic для валидации конфигов
5. Внедрить dependency injection

### Код
1. Вынести генерацию конфига в отдельный сервис `ConfigGeneratorService`
2. Вынести преобразование путей в отдельный сервис `PathMapperService`
3. Добавить репозитории для работы с файлами
4. Добавить обработку ошибок и retry логику для SSH
5. Добавить логирование действий пользователя

### Безопасность
1. Шифровать SSH-ключи
2. Добавить подтверждение действий пользователя
3. Валидация конфигов перед отправкой на сервер
4. Ограничить права пользователя на сервере
5. Добавить аудит действий

### Тестируемость
1. Добавить unit тесты с моками
2. Выделить интерфейсы для всех внешних зависимостей
3. Добавить интеграционные тесты для SSH
4. Использовать pytest с моками Qt

### Документация
1. Добавить документацию по API сервисов
2. Добавить диаграммы последовательности
3. Добавить руководство по развертыванию
4. Добавить changelog

## 10. Заключение

LLM-Control v2 — функциональное приложение с богатым функционалом, но с серьёзными архитектурными проблемами. Смешение UI и бизнес-логики, отсутствие тестов, проблемы безопасности — всё это требует рефакторинга.

Рекомендуется провести рефакторинг поэтапно, начиная с выделения бизнес-логики из UI и добавления тестов. Только после этого можно говорить о стабильности и безопасности приложения.
